LION’s metadata: results that can be made again¶

Every model LION saves carries the information needed to make it again: the model, the data it was trained on and how they were simulated, how it was trained, and the code and machine it ran on. From these records LION can make any component again, change it and train again, evaluate and compare models fairly, and publish a model as a self-contained package. This page describes what is recorded, how to use it, and what a new component needs to take part.

The model file¶

A model is saved as two files with the same name, as a solver saves it (solver.save_final_results()) or by hand (model.save(file, dataset=..., training=...)):

  • model.json: the metadata, plain JSON written by LION (read-only in intent):

    • lion_format: the metadata format’s version (a file without it, from before LION’s metadata, isn’t read);

    • model: the model’s spec (its class and parameters, see below);

    • environment: the environment record (LION’s code, packages, machine);

    • dataset_params: the data record of the training data;

    • training: the training record;

  • model.pt: tensors and plain values only, read with torch’s safe loader (weights_only=True), so loading a file runs no code from it:

    • model_state_dict: the weights;

    • initial_random_state: torch’s random state when the model was made (see Repeating a training exactly);

    • for checkpoints, also the optimizer’s (and scheduler’s) state, the epoch, the losses and the random state of the run.

Loading it: model, options, data = LIONmodel.load("model") makes the class the file names, with its weights; DnCNN.load("model") makes a DnCNN. Loading a file saved with other LION code gives a warning saying how the code differs.

Specs: components written as calls¶

LION writes a component as the call that makes it (LION/utils/spec.py), in JSON: a dict with "_target_" means “call this”, its other keys are the keyword arguments ("_args_": positional ones), and "_call_": false refers to a class or function without calling it. The keys follow Hydra’s instantiate convention.

{"_target_": "LION.experiments.ct_experiments.LowDoseCTRecon",
 "experiment_params": {"_target_": "LION.utils.parameter.LIONParameter", "name": "...", "...": "..."},
 "dataset": "LIDC-IDRI"}

  • Writing. A component’s spec is made from its attributes with the names of its constructor’s arguments (the same-name rule: LION’s components keep each argument as an attribute of the same name; a class that can’t defines spec_kwargs()). Tuples, numpy arrays, enums, paths, partials and classes are written so they come back as they were. A lambda, or a class that keeps no record of its arguments, can’t be written: records then only name it ({"unsaved": ..., "reason": ...}), with a warning, and it can’t be made again.

  • Building. A spec names code to run, so only classes in allowed modules are imported and called: LION’s, torch’s layers, losses and optimizers, and a few builtins (spec.ALLOWED_MODULES, ALLOWED_TARGETS). Your own classes are allowed by passing their module: allow=["my_package."]. A file never widens what may be built; only the caller does.

The records¶

Records are what LION writes about a component. They are LIONParameters (read with attributes, record.epochs.done), saved as plain JSON; the specs inside them stay dicts, describing objects that are made only when asked.

Repeating a training exactly¶

A training is repeated exactly when its data, initial weights and random numbers are the same:

  • Data. Simulated noise is drawn per sample from the experiment’s noise seed (noise_params.seed, default 0), inside LION.utils.rng.seeded(seed, <sample>): each sample is the same in every epoch, run and data loader worker.

  • Initial weights. A model keeps torch’s random state from when it was made (initial_random_state, saved in the .pt). When training starts, the solver checks that the model made again from that state has the same weights, and records {"from": "random_state"}. If not (a pretrained or custom start, layers made on a GPU), it saves the weights next to the results (<name>_initial.pt) and records {"from": "file", ...}. LIONmodel.instantiate(file, initial_weights=True) makes them again.

  • Fine-tuning. A model loaded with LIONmodel.load and trained again records where its weights came from: initial_weights.origin is the original’s file and its weights hash, so a fine-tuned model’s file leads to its original’s records. Weights loaded otherwise (e.g. load_state_dict) are saved, with origin: None and a warning.

  • Training’s random numbers. Solvers take a seed (default 0; None: unseeded) and seed torch, numpy and Python’s random when training starts. Checkpoints keep the random state, so a resumed run continues exactly as the uninterrupted one would. Validation doesn’t change training’s random numbers.

  • Determinism. On the CPU, the same code and package versions give the same model. On a GPU, runs with the same seed differ slightly (about 1e-3 in the weights after a few epochs) unless the solver is made with deterministic=True (slower). torch’s CPU and GPU random generators differ, so a seed gives different (equally valid) noise on each.

Making things again from a file¶

Each component makes itself again from a saved file (a model file, a data, training or test record, a spec, or a package’s files):

made again

its parameters, to change

made with changes

Model

LIONmodel.instantiate(file) (new weights); LIONmodel.load(file) (trained weights); instantiate(file, initial_weights=True)

LPD.parameters_from_file(file)

LPD.instantiate(file, model_parameters=parameters)

Experiment

Experiment.instantiate(file)

Experiment.parameters_from_file(file)

Experiment.instantiate(file, experiment_params=parameters)

Dataset

LIDC_IDRI.parameters_from_file(file)

LIDC_IDRI.instantiate(file, parameters=parameters)

Solver

LIONsolver.instantiate(file, model)

LIONsolver.parameters_from_file(file)

LIONsolver.instantiate(file, model, solver_params=parameters)

Reconstructor

LIONReconstructor.load(file) (with its model); LIONReconstructor.instantiate(file_spec_or_test_record, model=None) (another model, or none: running without one is an error)

PnP.parameters_from_file(source)

PnP.instantiate(source, model, parameters=parameters)

Evaluation

Evaluation.instantiate(test_record)

Evaluation.instantiate(test_record, samples=10)

  • Called on a base class (LIONmodel, Experiment, …) these make the class the file names; called on a class, that class, with a warning if the file names another.

  • parameters_from_file gives what default_parameters() gives, but as the file recorded it: start from an old experiment and change one or two things.

    parameters = LPD.parameters_from_file("results/lpd/final")
parameters.n_iters = 5
model = LPD.instantiate("results/lpd/final", model_parameters=parameters)  # new weights

  • instantiate(file, **arguments) replaces any recorded argument.

  • An experiment’s data, noise included, are made with Experiment.instantiate(file).get_dataset(record.split). The experiment classes differ only in their default parameters, so an experiment made with another experiment’s parameters gives a warning: it would be that experiment, recorded under the wrong class.

Evaluating and comparing¶

LION.evaluation scores reconstruction methods on a test set and keeps the results as test records:

from LION.evaluation import Comparison, Evaluation

evaluation = Evaluation(LowDoseCTRecon())            # the experiment's test split, PSNR/SSIM/HaarPSI
record = evaluation.run("results/lpd/final")          # a model or reconstructor file, a solver, a reconstructor or a function
comparison = Comparison(evaluation, ["results/lpd/final", "results/fbpconvnet/final"])
comparison.run()                                      # the baseline (FDK for CT) first
comparison.save("comparison")                         # records, tables, per-sample scores, figures

  • Records are saved (in $LION_RESULTS_PATH/evaluations by default) and reused when the same method is run on the same evaluation again.

  • From the models’ records, a comparison checks that it is fair: a model trained or validated on test data is an error (checked by patient for LIDC-IDRI), a model trained on another problem or with other LION code gives a warning.

  • Comparison.instantiate(folder) makes a saved comparison again.

Publishing a model¶

LION.package.publish writes everything needed to make a model, train it again and test it, in one folder:

from LION.package import publish
publish("results/lpd/final", "lpd_package", evaluation=evaluation)  # evaluation: optional
publish("results/pnp", "pnp_package")   # a reconstructor's file: its model, and the reconstructor

lpd_package/
  model.json, model.pt   the model file, exactly as LION saved it
  <name>_initial.pt      the initial weights, when the solver saved them
  experiment.json        the experiment
  data/training.json     the training data's record
  data/validation.json   the validation data's record, if validated
  solver.json            the training record
  test.json              the test record, if an evaluation was given
  reconstructor.json     the reconstructor, when one is published (its model: model)
  environment.txt        the packages installed where it was published (conda's and Python's)
  package.json           the files' sha256, the citations, LION's version and commit, notes
  README.md              a model card, generated (edit it freely: it isn't checksummed)

  • It refuses (an error, before writing anything):

    • LION code that isn’t committed and pushed, now and when the model was saved and tested;

    • a file without a training or data record;

    • records naming code outside LION, or what could only be named (a lambda);

    • what training again would miss: unsaved initial weights, seed=None, data not made by an Experiment, or data outside LION_DATA_PATH;

    • a test of other weights, or on data the model was trained or validated on;

    • for a fine-tuned model, an original (and its original, …) that is missing, has other weights than training started from, or would be refused itself;

    • a folder that isn’t empty.

  • A fine-tuned model’s originals are in the package: their metadata as origin/model.json (and origin/origin/model.json, …), and the model card lists them. train_again repeats the last training, from the saved initial weights.

  • Notes (in package.json and the model card): a package published in another environment than it was trained in, tested on another problem, or trained from weights whose origin isn’t recorded.

  • Citations are each component’s cite(): where the model, solver and dataset come from (their papers), not the work being published.

  • The model card describes the model, the problem, the training and the test, and shows how to use and train the model again, step by step.

Using a package¶

from LION.package import build, load, load_and_build, train_again

package = load("lpd_package")        # the recorded arguments, to change; nothing made yet
package.model.model_parameters.n_iters = 5
package.experiment.experiment_params.noise_params.I0 = 5000
package.optimizer.lr = 1e-4
package.training.epochs = 20

built = build(package)               # model, experiment, data, solver (data set), evaluation, reconstructor
built = load_and_build("lpd_package")        # as published
model = train_again(package, "retrained")    # trained again, changed or not

  • load warns about files changed since publishing, and about LION code other than the model was saved with.

  • build gives the model its trained weights, or with initial_weights=True the ones training started from; a model whose arguments were changed starts from new random weights.

  • Everything runs on the device the model was trained on unless device= says otherwise (on the CPU if it was a GPU and there is none).

  • Unchanged, train_again gives the published weights (on the CPU, or on a GPU with a deterministic solver).

Folders: LION_DATA_PATH and LION_RESULTS_PATH¶

  • LION_DATA_PATH is where the datasets are; LION_RESULTS_PATH (optional) is where solvers save by default. Both are read when a path is used.

  • Paths inside them are written relative to them, as data_path("...") and results_path("..."), so a file means the same folder on any machine. A path outside them is written as it is, and publish refuses data outside LION_DATA_PATH.

  • Where a machine saves (save_folder) and where it runs (device, verbose) are not recorded.

For developers: making a component take part¶

A new model, dataset, experiment, solver or reconstructor takes part when:

  • it derives from LION’s base class (LIONmodel, LIONDataset, Experiment, LIONsolver, LIONReconstructor), which gives it instantiate, parameters_from_file and its records;

  • it keeps each constructor argument as an attribute of the same name (self.model_parameters, self.operator_params), or defines spec_kwargs();

  • its settings are a LIONParameter with a static default_parameters(); a setting added later reads getattr(parameters, "name", <old behaviour>), so files saved before keep giving their results;

  • it is made only from LION’s classes and functions (a functools.partial of a LION function, not a lambda), so its spec can be built again;

  • datasets list their samples (sample_ids(), and sample_files()), and sample_groups() where samples come in groups that must stay in one split; random numbers that make up the data are drawn inside rng.seeded(...);

  • solvers keep values they compute during a run in solver_params (starting as None), so they are recorded and come back on resume;

  • it defines cite() if it comes from a paper.

What isn’t covered¶

  • The data themselves: records identify the data (sample IDs, how they were simulated) but don’t contain them, and a package doesn’t either (they are large and licensed by others). A file-content hash can be asked for (data_record(dataset, hash_files=True)).

  • Code outside LION: specs can name it (with allow=), but LION only records its own code’s commit, and only LION’s classes can be published.

  • Bitwise GPU results without deterministic=True, or across different versions of torch, CUDA or the hardware.

  • Files saved before this system (October 2026) load as before, with whatever they recorded.
